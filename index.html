02 / EXECUTION MAP

Follow the six steps.

This is the original execution order. Hardened behavior is called out separately; the external installer’s internals are outside this file.

  1. 01 → Validate
  2. 02 → Dependencies
  3. 03 → Download
  4. 04 → Install
  5. 05 → Service
  6. 06 Join
01

Validate the request

The original lowercases the network ID, checks exactly 16 hex characters, requires root and reads /etc/os-release. An existing CLI skips steps 2–4.

L174–199
Original / validation excerpt
NETWORK_ID="${1,,}"
[[ "$NETWORK_ID" =~ ^[0-9a-f]{16}$ ]]
[[ $EUID -eq 0 ]]

Excerpt only; the original attaches error handlers. Revision: checks the package and unit, restricts PATH, and acquires a single-run lock.

02

Prepare the dependencies

Only when the CLI is absent, the original refreshes APT and installs curl, gnupg and certificates. Noninteractive variables are set before the main sequence.

L19–20, L209–214
Original / package commands
apt-get update -qq
apt-get install -y -qq curl gnupg ca-certificates

Expected: package operations return zero. Revision also installs python3 for JSON status parsing. APT locks or broken sources can still stop installation.

03

Download the installer

The original saves the HTTPS response to a temporary file and retries transfers. A complete download is not a separate integrity or signature check.

L224–229
Original / download command
curl -fsSL --retry 3 --retry-delay 2 \
  https://install.zerotier.com -o "$TMP_INSTALLER"

Revision: limits transfer time, requires HTTPS redirects, rejects an empty file and compares its SHA-256 against the independently supplied value.

04

Execute the downloaded code

The original passes the file to Bash as root. Its comments describe APT repository setup, but that downloaded implementation is not included in the reviewed source.

L235–243
Original / trust boundary excerpt
run "Running the installer" bash "$TMP_INSTALLER"

Revision executes only matching bytes, then checks that the CLI and Debian package exist. Hash matching does not audit repository keys or later downloads.

05

Start the local service

The original enables the daemon at boot, starts it and polls zerotier-cli info up to 30 times. A responsive local daemon may still be offline.

L152–158, L252–255
Original / service command
systemctl enable --now zerotier-one

Revision bounds each readiness call to two seconds, with one-second intervals. Thirty attempts can take roughly 90 seconds plus process overhead.

06

Request network membership

The original submits the join, prints identifiers and network details, and reminds the operator to authorize a private member. It does not wait for an operational network.

L263–290
Original / join command
zerotier-cli join "$NETWORK_ID"

Illustrative CLI acknowledgement: 200 join OK. Revision separately reads JSON membership status and reports pending authorization.

Endpoint scope: the original main sequence contains no UFW, iptables, routing or IP-forwarding commands (L174–265). Those changes require a separate routing and access policy; external installer side effects are not established here.

04 / STATIC CODE REVIEW

Fix the trust boundary first.

Original verdict: unsuitable for unattended production use under the requested verification policy. The revision reduces identified risks; Ubuntu runtime behavior remains untested.

9 findings shown.

IMP-01 HIGH

Remote code runs as root without a separate integrity check

Require reviewed installer bytes and a matching SHA-256 before Bash execution. HTTPS remains necessary; the hash trust source remains the operator’s responsibility.

L225–241
IMP-02 MEDIUM

Unsupported hosts proceed after a warning

Fail before package changes unless Ubuntu 22.04, systemd and the required tools are available. This intentionally narrows the accepted platform.

L184–191, L210–211, L254
IMP-03 MEDIUM

Identifiers and raw diagnostics reach the terminal

Hide IDs from wrapper messages, retain command output in a private log and stop automatically printing its tail. Network IDs identify networks; authorization is controlled separately.

L130, L144, L178–181, L263–290
IMP-04 MEDIUM

Retries do not create a time limit

Bound curl connections and transfers, each daemon probe and the join call. Package installation and the vendor script remain unbounded to avoid interrupting package transactions.

L154–156, L227, L265
IMP-05 MEDIUM

The completion banner overstates network readiness

Report “join request submitted,” inspect JSON membership status and distinguish pending approval from a reported network error.

L265, L280–290
IMP-06 MEDIUM

CLI presence alone decides whether to skip installation

Check the Debian package and service unit before skipping. A partial or custom installation requires manual reconciliation.

L196–199, L209, L240–254
IMP-07 MEDIUM

Background execution lacks a cancellation policy

Run commands in the foreground, add signal exit codes and serialize wrapper instances. Interruptions can still leave completed changes; the wrapper offers no rollback.

L46, L124–146, L174–265
IMP-08 LOW

No help, dry run or explicit motion controls

Add early help, a side-effect-free plan, verbose executable names and NO_COLOR / --no-color support. Keep the six steps and a shorter retro banner.

L29–35, L165–181, L280
IMP-09 LOW

Command failure codes and log discovery are inconsistent

Preserve the failing command code and always print the private log path. Use an explicit umask and private work directory; the original mktemp files already have restrictive permissions.

L40–46, L117–119, L129–145

DNS / EVIDENCE TO RECOVERY

When the hostname will not resolve.

The supplied terminal screenshots show a DNSSEC validation failure during ZeroTier setup. The sequence below separates the observations, possible causes and recovery choices.

OBSERVED IN THE SCREENSHOTS

DNSSEC validation failed: missing-key

Disabling DNS-over-TLS alone still left the lookup failing. A later lookup returned addresses after DNSSEC was also disabled; its result explicitly reported unauthenticated data.

curl: error 6→DNSSEC missing-key→Answer with validation off

Interpretation: this is evidence of a validation-path issue, not proof that the authoritative zone, host clock, trust anchors or upstream resolver caused it. No root cause was established on the actual host.

SCREENSHOT 1

curl cannot resolve the host

Error 6 means hostname resolution failed. It does not establish a package, authorization or HTTPS certificate failure. Running curl without a URL only prints usage.

Official curl error reference
SCREENSHOT 2

Inspect global and per-link policy

The screenshot shows link ens6, a DNS routing domain ~. and DNS-over-TLS enabled. ens6 is specific to that host; discover your interface before changing it. A global setting alone may leave a link override effective.

Resolver policy reference
SCREENSHOTS 3–5

Keep validation and encryption separate

DNSSEC validates DNS data. DNS-over-TLS protects the resolver transport. Turning off TLS did not remove the missing-key error in these images; turning off validation allowed an unauthenticated response.

The returned IP addresses are a point-in-time result, not values to hard-code.
SCREENSHOT 6

A route and overlay address are present

The displayed route and assigned ZeroTier address establish local configuration at that moment. They do not establish working DNS, an Internet path or application reachability. The Ubuntu update notice alone cannot identify which layer failed.

Screenshot summaries are sanitized; private network details and raw images are not published.
01

Capture the active state

Run diagnosis on the Ubuntu host. It checks a fresh resolver lookup and the application's NSS path, reports interface policy and time, and compares one validation-bypassed lookup only if normal resolution fails.

Exit 3 means only the bypassed comparison succeeded. Exit 2 means lookup failure; exit 1 covers local prerequisites or commands. Diagnosis does not write configuration.

Read-only DNS diagnosis
ip route show default
resolvectl --no-pager status
timedatectl show -p NTPSynchronized -p TimeUSec
bash fix-zerotier-dns.sh --diagnose

Keep this output local or redact it before sharing: routes, addresses and DNS policy may be sensitive.

02

Isolate the validation path

Compare uncached answers. If the normal query fails with missing-key while the bypassed query works, investigate the clock, current trust-anchor/software updates, upstream DNSSEC handling and the DNS network path. These are hypotheses to test.

A successful bypass is diagnostic evidence; it does not authenticate the answer or prove the DNS data is correct.

Compare one query without DNSSEC validation
resolvectl --cache=no query install.zerotier.com
resolvectl --cache=no --validate=no query install.zerotier.com

resolvectl documents --validate and --cache. The comparison disables validation only for that query.

03

Try a policy-preserving refresh

The refresh mode clears cached answers and learned server capabilities, then rechecks DNS and NSS. It keeps DNS servers, security policies, Netplan and routing unchanged. It cannot repair every validation failure.

Refresh resolver cache and learned server features
sudo bash fix-zerotier-dns.sh --refresh

If it still fails, inspect the upstream path and trust configuration rather than repeatedly restarting network services over SSH.

04

Use a temporary exception deliberately

If diagnosis justifies a short recovery window and your policy permits it, choose the affected link explicitly. This command disables DNSSEC for all queries using that link. It is not limited to the ZeroTier hostname.

DNS-over-TLS remains unchanged. Add --disable-dot only if a separate transport problem justifies losing encrypted DNS. No DNS server address is replaced.

Explicit temporary DNSSEC workaround
read -r -p 'Affected interface from resolvectl status: ' IFACE
sudo bash fix-zerotier-dns.sh --workaround \
  --interface "$IFACE" --disable-dnssec

The helper saves the previous effective policies in a root-private /run directory. A failed lookup or interruption triggers a restoration attempt; failed recovery leaves the record for manual review.

05

Restore and fix the underlying policy

Restore promptly and inspect the result. The helper restores saved effective values as explicit runtime settings; it cannot reconstruct the previous inheritance from network-manager configuration.

It refuses a stale snapshot if the resolver process or interface identity changed. Reboot or network reconfiguration may supersede runtime changes. This is a reversible workaround, not a permanent repair.

Restore saved effective link policies
read -r -p 'Interface used for the workaround: ' IFACE
sudo bash fix-zerotier-dns.sh --restore --interface "$IFACE"
bash fix-zerotier-dns.sh --diagnose

For a durable repair, review the owning Netplan, systemd-networkd, NetworkManager or cloud configuration. Update clock/trust/software or DNS policy at that source. Avoid overwriting resolv.conf or globally disabling DNSSEC as an automatic default.

06

Verify HTTPS and installation separately

After DNS recovers, test a bounded HTTPS transfer with certificate checking intact. A failure may require separate proxy, firewall, route, time or certificate diagnosis. Do not add curl -k, pin the screenshot's IP addresses or pipe a downloaded script into Bash.

Check HTTPS separately after DNS recovery
curl --proto '=https' --proto-redir '=https' \
  --connect-timeout 5 --max-time 20 -fsSL \
  -o /dev/null https://install.zerotier.com
printf 'curl exit: %s\n' "$?"

Expected for successful verified transfer: curl exit 0. This probe discards the response and executes nothing. Resume the reviewed installer using an independently approved upstream SHA-256.

Why this helper differs from the screenshot commands: the images edit a persistent global drop-in and restart the resolver. The helper uses explicit per-link runtime changes with saved effective policy values. It does not delete or override an existing dns.conf; those prior edits still need an administrator's review. It also leaves DNS server addresses, routing, firewall and services unchanged.
What if global DNS servers and link DNS disagree?
Inspect both in resolvectl status. The ~. routing domain can direct queries to the link. FallbackDNS is used when no other DNS server information is known; it is not a guaranteed failover for a broken configured server. Choose resolvers approved for your network; public resolvers can break split DNS or expose private queries. Read DNS routing and fallback rules.
Will this fix survive a reboot?
The helper's policy changes are runtime-only and may be replaced earlier by a network manager. Its private saved state lives under /run and is not a persistent backup. Diagnose and fix the actual managing configuration for a durable result. No automatic global DNSSEC exception is installed. Netplan configuration reference.
Can I preview the helper without touching the host?
Yes. Help and dry-run return before host checks or network operations. ens6 here is only the interface shown in the supplied screenshots; replace it with your actual link for a real operation.
Inspect the DNS helper plan
bash fix-zerotier-dns.sh --help
bash fix-zerotier-dns.sh --workaround --interface ens6 \
  --disable-dnssec --dry-run

Scope: Ubuntu 22.04 with an already active systemd-resolved instance. No live DNS correction was performed on your server. Static checks and isolated mocked recovery tests are reported in REVIEW.md. The default diagnostic mode may make DNS queries, but changes no configuration.

05 / FAILURE AND RECOVERY

Read the failure state.

Use these diagnostic paths to investigate your host; no runtime results were observed here. Reconcile host and controller state before retrying an interrupted installation.

Why does the revision require an installer hash?
The original downloads a mutable URL and immediately executes its contents as root (L225–241). The revision requires an independently approved digest. Review the exact installer bytes in your trusted release process; use the resulting hash for those bytes. A changed upstream installer will fail closed. A matching digest does not verify its later downloads or prove the code is safe.
Why is ACCESS_DENIED still shown after a successful join?
The join request and controller authorization are separate. Inspect the node identity locally, then authorize the intended device in the network owner’s trusted Central account. The original already warns about manual approval (L260–265, L289–290). REQUESTING_CONFIGURATION can also be transient; inspect status again to establish the current state.
What if the daemon never becomes ready?
The original retries a local CLI call (L152–158). The revision bounds individual probes, but package, unit, permissions or daemon failures still need diagnosis. Inspect the service journal locally; redact sensitive output before sharing.
Local diagnosis / potentially sensitive output
sudo journalctl -u zerotier-one -n 80 --no-pager
Should I enable forwarding or add a firewall rule?
The original does neither (main sequence L174–265). An endpoint join is separate from routing traffic for other hosts. Inspect your local firewall and ZeroTier interface policy against the official router guidance. Do not enable forwarding or broadly open interfaces without a routing requirement.

Read official router and firewall guidance

Can I rerun the installer after an interruption?
The original claims repeatability but uses CLI presence as its installation test (L11–12, L196–199). The revision rejects an inconsistent CLI/package/unit combination and uses a wrapper lock. This is not transactional rollback: APT changes, service starts or a submitted join may already have happened. Inspect the private log, package state, service and memberships first. Do not remove an APT lock held by another process.
What does the revision’s exit code mean?
Zero means the request was submitted and its observed membership state was accepted or pending; it does not prove service reachability. Code 2 indicates a reported network failure or unknown state, 130 an interrupt and 143 termination. Other failures preserve command codes where possible; code 1 is also used for local validation errors. These codes apply to the revision only.
Does dry run simulate the downloaded script?
No. It prints the revision’s plan without creating files, contacting the daemon, downloading or changing packages. It does not validate the host, discover installed state or predict the vendor installer’s side effects. The original has no dry-run option (L176–181).

06 / TRUST AND SCOPE

Keep the boundary explicit.

Root is required by both scripts for package and service changes (original L181, L210–211, L254). No compliance certification or production test is implied.

OPERATOR POLICY

Protect the host and its identity

  • Approve installer bytes through a trusted review process. Track repository keys and downstream packages separately.
  • Protect ZeroTier identity files and authentication tokens. Neither script needs a Central API token.
  • Restrict access to retained logs. The revision’s wrapper hides IDs, but vendor and CLI output in its private log may contain them.
  • Limit overlay access to the intended services. Authorization alone does not define a least-privilege application policy.
ASSUMPTIONS & VERIFICATION

What still needs a real host

  • Actual Ubuntu version, CPU architecture, repository package availability and systemd health are not proven by this static review.
  • DNS, HTTPS access, APT sources, controller access and firewall behavior depend on your environment.
  • The external installer’s contents, repository signing setup and runtime effects are outside the original file.
  • Verify in a disposable Ubuntu 22.04 environment before deployment. This review did not execute either installer.
